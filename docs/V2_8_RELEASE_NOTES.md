# research-paper-workflow v2.8 — Release Notes

Date: 2026-10-07  
Release class: **MINOR**

## Problem and resulting behavior

v2.7 already provided strong source/novelty controls and independent mathematical/scope certification. It left candidate deduplication, exploration budgets, short contribution records, and related-result dependencies less explicit. v2.8 connects those records to the next research investment inside the existing Stages.

## Changes

- Stages 0/3: source-grounded candidate IDs, structural deduplication, finite batch budgets, dispositions and reopening reasons; broader banks remain optional.
- Stages 2/6: exact closest-paper/source-claim comparison and reading-depth evidence; scores do not certify novelty.
- Stages 3/4/6: short provisional contribution memos, updated at Stage 6 against certified results before discretionary Stage-7 expansion.
- Stage 4A: reviewer input exposure, independent attack path, and discrepancy reconciliation records.
- Stages 7/8: bounded related-result/dependency scope with core/robustness/Appendix/future/rejected dispositions; grouping transfers no certificate.
- Correction/reassessment: route-appropriate evaluation of substantive corrected conclusions, with unchanged inherited certification.
- Stage 8: certificate-name synchronization with the canonical Stage-7.5A portability wording.

Companion format: `templates/RESEARCH_SEARCH_REGISTER.md`; equivalent existing records suffice. There is no universal candidate, random-draw, extension, or manuscript quota.

## Compatibility and migration

No Stage is added, removed, renumbered, redefined, or rerouted. Verdict semantics, one-fix discipline, rollback, freeze meanings, and formal-verification requirements remain intact. This is a substantive check/evidence refinement, hence MINOR rather than PATCH.

Active projects apply the new content at the next relevant Stage. Do not reconstruct imaginary historical logs or automatically thaw frozen/submitted projects. Material new defects use existing rollback. The final design record explains adopted/rejected options and migration.

The prior v2.7 stable tag remains immutable. Readiness/version markers do not by themselves establish that the v2.8 tag/Release exists; GitHub publication is checked separately.
